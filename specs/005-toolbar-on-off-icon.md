# 005 — Toolbar ON/OFF icon

GitHub issue: https://github.com/SlobodanBogdanovic/APIResponseSimulator/issues/3

`specs/002-toolbar-on-off-status.md` already paints the badge and the tooltip from `settings.extensionEnabled`. This spec replaces the solid-square toolbar icon and switches the artwork with that same switch. Badge text, badge colors, and tooltip strings stay as spec 002 defined them.

## Who is the user and what problem do they have

The user is a developer or QA person using **API Response Simulator** while their app calls an API. They turn mocking on or off with the switch in the popup header, then go back to the app.

The toolbar button is a solid indigo square, generated by `scripts/gen-icons.mjs`. On `chrome://extensions` the card has no real icon, because the manifest has no top-level `icons` key. The extensions menu shows that same placeholder. The letters ON and OFF on the badge are the only status on the button. The artwork does not change when the switch is off, and it does not look like a finished extension icon.

## Problem

The shipped icon is the solid square at `public/icons/icon16.png`, `public/icons/icon48.png`, and `public/icons/icon128.png` (copied to `dist/icons/` by the build). `action.default_icon` points at those three files. Nothing in the manifest declares `icons`. `paintToolbarStatus` in `src/background/service-worker.ts` calls `chrome.action.setIcon` with those same three paths for both on and off.

The JetBrains Mono PNGs are already in `assets/icons/`. Vite’s `publicDir` is `public/`, and the first build uses `emptyOutDir: true`, so files that stay only under `assets/icons/` never appear in `dist/`. A path in the manifest that does not exist in `dist/` is a missing icon.

The gray PNGs are unused. The service worker does not choose an icon from the stored switch.

## Expected user outcome

The user looks at the toolbar button and sees a rounded square. On that button the letters read **API**. The 16px files draw that one line and do not draw **sim**. The 32px files draw a second line that is not readable as **sim** at 16 CSS pixels. The user tells the switch by color: the indigo glyph when the switch is on, the gray glyph when the switch is off.

When the extension’s own switch is on, the icon is the colored indigo glyph. When that switch is off, the icon is the gray glyph. The badge and the tooltip stay in step with the icon: ON with the colored glyph, OFF with the gray glyph.

The user flips the switch in the popup, closes the popup, and sees the new icon within one second, without opening the popup again. Every window shows the same icon.

On `chrome://extensions` the card shows the colored glyph when the switch is on and when the switch is off. That card does not turn gray. The extensions menu shows the same icon as the toolbar button: colored when the switch is on, gray when the switch is off, and the colored default before the first paint. None of these surfaces shows the solid square.

After a browser restart, an install, a reload from `chrome://extensions`, or a service worker restart, the toolbar icon matches the saved switch once the worker has painted. A first install shows the colored glyph. Until that paint, Chrome may show the manifest default, which is the colored glyph. That moment is not a settled status. The user does not open the popup to make the icon match.

## User story

As a developer or QA person using the extension, I want the toolbar icon to be the JetBrains Mono glyph and to turn gray when the global mocking switch is off, so I can see the switch from the toolbar and the extension no longer shows a placeholder square.

## Scope

One PR. Ship the provided JetBrains Mono PNGs and switch the toolbar icon with the existing global switch.

“Enabled” means `settings.extensionEnabled` in `chrome.storage.local`. It is the extension’s own mocking switch. It is independent of Chrome’s enable/disable control on `chrome://extensions`, and independent of each rule’s `enabled` flag.

When a `settings` object is present, the icon uses the same truthiness rule as the popup header switch, the interceptor, and `isExtensionOn` in the service worker: a truthy `extensionEnabled` is on, and a falsy `extensionEnabled` is off. Falsy includes `false`, a missing field, `null`, `0`, and `""`. A truthy non-boolean is on. An absent `settings` key and a failed read are on, the first-install default. A failed read does not write that default.

The saved value lives in `chrome.storage.local` under `settings`. The service worker reads that stored value whenever it paints. A boolean that exists only in service-worker memory is not the source of truth. `toolbarPaintGeneration` may stay as the in-memory guard that stops a slower read from covering a newer change. It is not the switch.

### Where the files are loaded from

`public/manifest.json` is the manifest Vite copies to `dist/manifest.json`. Vite’s first config (`vite.config.ts`) has `publicDir` set to `public/` and `emptyOutDir: true`, so a file must be written into `dist/` after that wipe, or be present in `public/` before the first build, or it will be missing from the unpacked extension. The content and bridge configs keep `emptyOutDir: false` and must not wipe `dist/`.

`npm run build` byte-copies these six files from `assets/icons/` to `dist/icons/` with the same filenames:

- `icons/icon-16.png`
- `icons/icon-32.png`
- `icons/icon-48.png`
- `icons/icon-128.png`
- `icons/icon-16-off.png`
- `icons/icon-32-off.png`

The copy uses Node `fs.copyFile` (or `copyFileSync`) from `node:fs`. It does not decode or re-encode the PNG. Paths resolve from the repo root. Vite’s `root` is `src/`, so a relative `assets/icons` path from that root would miss the files. The copy runs for `vite build` and for `vite build --watch`, and it still holds after the other two builds in `npm run build`. `npm run dev` is that watch build.

The copy lives in `vite.config.ts`. No new npm package. `package.json` dependencies and devDependencies stay as they are. `npm run build` does not run `npm run icons`.

Delete `public/icons/icon16.png`, `public/icons/icon48.png`, and `public/icons/icon128.png` so the build stops shipping the solid squares. After `npm run build`, `dist/icons/` does not contain `icon16.png`, `icon48.png`, or `icon128.png`.

### One toolbar function

`paintToolbarStatus` in `src/background/service-worker.ts` is already the only function that paints the toolbar. Extend that function. Do not add a second painter.

From the same boolean it already receives, it sets all of the following, and no other function calls these APIs:

- badge text (`chrome.action.setBadgeText`)
- badge background (`chrome.action.setBadgeBackgroundColor`)
- badge text color (`chrome.action.setBadgeTextColor`)
- tooltip (`chrome.action.setTitle`)
- toolbar icon (`chrome.action.setIcon`)

Badge text stays exactly `ON` or `OFF`. Background stays `#137333` for on and `#5F6368` for off. Text color stays `#FFFFFF`. Tooltip stays exactly `API Response Simulator: ON` or `API Response Simulator: OFF`. Those strings are specified in `specs/002-toolbar-on-off-status.md` and do not change here.

`setIcon` is called with no `tabId` and no `imageData`. The path map has sizes 16 and 32 only:

| Resolved boolean | `path["16"]` | `path["32"]` |
|---|---|---|
| on | `icons/icon-16.png` | `icons/icon-32.png` |
| off | `icons/icon-16-off.png` | `icons/icon-32-off.png` |

Numeric keys `16` and `32` are the same as the strings `"16"` and `"32"`. The path map does not include 48, 128, or the old names `icons/icon16.png`, `icons/icon48.png`, and `icons/icon128.png`.

`isExtensionOn` stays the resolver. `paintToolbarFromStorage` stays the reader. The worker still calls the paint path:

- once at worker startup, after the listeners are registered
- from `chrome.runtime.onInstalled`
- from `chrome.runtime.onStartup`
- from `chrome.storage.onChanged` when the area is `local` and the changed key is `settings`

Those listeners stay registered at the top level of the service worker, before any `await`. The `OPEN_OPTIONS` behavior stays. A change to the `rules` key does not repaint the toolbar. The install path still writes `{ extensionEnabled: true }` only when `settings` is absent.

The popup header switch is the only control that writes `extensionEnabled`. It already calls `saveSettings`. The service worker hears that write through `chrome.storage.onChanged`. The popup does not call `setIcon`. The options page has no global switch. Toggling a rule does not change the icon.

### When `setIcon` or the storage read fails

A failed storage read still paints the default ON state and does not write that default. The default ON state is the colored paths, badge `ON` on `#137333` with white text, and the tooltip `API Response Simulator: ON`.

`setIcon` can throw, return a rejected promise, or report `chrome.runtime.lastError`. `paintToolbarStatus` catches all three. None of them becomes an unhandled exception or an unhandled rejection.

If `setIcon` throws, returns a rejected promise, or reports `chrome.runtime.lastError`, `paintToolbarStatus` swallows that error. The badge text, badge background, badge text color, and tooltip stay on the resolved boolean. A failed icon call does not paint badge `ON` or the tooltip `API Response Simulator: ON` for an off value. When the resolved boolean is off, the function does not call `setIcon` again; the badge stays `OFF` on `#5F6368` with `#FFFFFF` text, and the tooltip stays `API Response Simulator: OFF`. The visible image may remain the colored manifest default, and the badge is the status. When the resolved boolean is on, the badge stays `ON` and the tooltip stays `API Response Simulator: ON`, and the function may try the colored paths once. A second failure is swallowed. There is no retry loop.

## Edge cases

- First run with no `settings` key. The settled icon is the colored glyph, the badge is ON, and the tooltip is `API Response Simulator: ON`. The install writer still stores `{ extensionEnabled: true }` only when the key is absent.
- Until the worker paints, the toolbar can show the colored `default_icon` and the tooltip can be only the extension name. That look is not a settled status, including when the saved switch is off. The settled gray icon appears after the paint, without opening the popup.
- When `settings` is present, truthy `extensionEnabled` selects the colored paths and falsy `extensionEnabled` selects the gray paths. Falsy includes `false`, a missing field, `null`, `0`, and `""`. A truthy non-boolean selects the colored paths. The interceptor, the bridge, and the popup stay unchanged.
- The `settings` key is deleted later. The icon returns to the colored glyph with the ON badge and tooltip.
- The user toggles the popup switch several times quickly. The icon, badge, and tooltip end on the last stored boolean within one second of that last toggle. An earlier read does not cover a later one.
- Two or more browser windows are open. `setIcon`, the badge calls, and `setTitle` omit `tabId`, so every window shows the same icon, badge, and tooltip.
- Reload from `chrome://extensions`, a service worker restart, and a browser restart read storage again. A stored off value stays gray. A stored on value stays colored. Reload does not write a new default over existing `settings`.
- `toolbarPaintGeneration` is cleared when the worker stops. The switch is read from storage on the next start. The worker does not keep the on/off boolean only in memory.
- The user turns individual rules on or off, imports rules, or edits a rule. The toolbar icon stays on `extensionEnabled`.
- The switch is on and every rule is disabled, or no rule matches. The icon stays the colored glyph.
- The user turns the switch off while a matching request is already in progress. The icon turns gray within one second. That request can still return the fake response. Interceptor behavior stays as it is today.
- `setIcon` fails because a path is missing or the API rejects the call. The badge and tooltip stay on the resolved boolean. A stored off value keeps badge `OFF` and tooltip `API Response Simulator: OFF`. The function does not try the ON paths for that off value, swallows the error, and does not throw.
- A failed storage read paints the colored ON state and does not write `settings`.
- Light toolbar theme and dark toolbar theme. On the toolbar, each glyph is readable as **API**, and color shows the switch. On the extensions card, the colored glyph is readable as **API** over **sim**. The theme does not choose which file is used. The switch does.
- `icon-48-off.png`, `icon-128-off.png`, and `master-512.png` stay in `assets/icons/` at the hashes above and are not manifest icons and not `setIcon` paths.
- `npm run icons` is not part of this build. Running it recreates solid squares at the old filenames. Those filenames stay out of the manifest and out of `setIcon`.
